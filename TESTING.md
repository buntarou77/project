## 1. Принцип: что мы запускаем, где живёт база, как ходят запросы

В проекте три способа запуска. Во всех трёх ядро бизнес-логики одно и то же
(`src/core`) — меняется только окружение.

### Режим ДЕМО — сервер и база не запускаются вообще
- **Процессы:** только Vite (localhost:5173), раздаёт собранный SPA.
- **База:** не используется. Данные (студия, заявки) лежат в localStorage браузера
  и берутся из `public/tenants/<slug>/tenant.json`.
- **Запросы к серверу:** их нет. Адаптер `src/backend/demo.ts` перехватывает все
  вызовы интерфейса `Backend` и работает с localStorage напрямую.
- **Когда:** показать образец фотографу, отладить вёрстку, прогон e2e-тестов.

### Режим ПОЛНОГО СТЕКА — ручное тестирование «как на проде»
Четыре процесса, каждый в своём терминале (или как сервис):

1. **PostgreSQL** — `localhost:5432`. Живёт в контейнере podman/docker (данные в
   volume) или как системный сервис (данные в `/var/lib/pgsql/data`). Логин/пароль
   и адрес — в `server/.env` (`DATABASE_URL`). Сама по себе база просто ждёт
   подключений по TCP; все таблицы создаёт `pnpm db:migrate`.
2. **Express API** — `server/`, порт 3000. При старте открывает пул соединений
   (`pg`) к Postgres и выполняет параметризованный SQL (`$1, $2…`). Все запросы
   к базе делает **только сервер** — браузер в базу не ходит.
3. **Мок ИИ** — порт 3100 (нужен, только если тестируете помощника).
4. **Vite** — порт 5173: раздаёт фронтенд и проксирует `/api/*` → `:3000`
   (same-origin, поэтому cookies авторизации работают без CORS).

Поток заявки: браузер → `:5173` → `fetch('/api/public/...')` → прокси Vite →
Express `:3000` → middleware (cookies → auth → rate-limit → Zod) → SQL через `pg`
→ PostgreSQL → JSON обратно → React Query обновляет экран.

### Интеграционные тесты — тот же стек, но управляемый и одноразовый
`pnpm test:integration` в `server/`:
- тест **сам поднимает встроенный Postgres** (embedded-postgres): данные во
  временной папке `server/tests/.pgdata`, порт 5433, после прогона стираются;
- применяет миграции к этой базе (`server/migrations`);
- поднимает Express **в памяти** (supertest — запросы идут без открытия сетевого
  порта, но проходят весь стек: middleware → SQL → реальный Postgres);
- сценарии стучатся HTTP-запросами как настоящий клиент и сверяют JSON-ответы.

### Прод — тот же полный стек, но на VPS
Postgres — systemd-сервис, API — systemd-сервис, фронт — статика в nginx.
Движок и диалект SQL те же, поэтому локальные тесты на Postgres = тесты продовой
базы.

| Режим | Процессы | База | Для чего |
|---|---|---|---|
| Демо | vite | localStorage | образец, вёрстка, e2e |
| Полный стек | vite + API + Postgres (+ мок ИИ) | PostgreSQL localhost:5432 | ручная приёмка |
| Интеграционные тесты | vitest + встроенный PG | одноразовая БД :5433 | инварианты API |
| Прод | nginx + API + Postgres | PostgreSQL на VPS | боевые данные |

## 2. Тестовая инфраструктура на Fedora 44

**Docker не обязателен** (зачем он вообще и как помогает при деплое — раздел 7).
Нужны две вещи: база и перехватчик писем. Выберите вариант.

### Вариант А — Podman/Docker Compose (на Fedora Podman предустановлен)

```bash
sudo dnf install podman-compose          # либо только podman, если compose есть
podman-compose -f docker-compose.dev.yml up -d

# если предпочитаете настоящий Docker CE:
sudo dnf config-manager addrepo --from-repofile=https://download.docker.com/linux/fedora/docker-ce.repo
sudo dnf install docker-ce docker-compose-plugin
sudo systemctl enable --now docker
docker compose -f docker-compose.dev.yml up -d
```

| Сервис | Порт | Зачем |
|---|---|---|
| PostgreSQL 15 | `localhost:5432` (user `postgres`, пароль `test`, база `photo_booking`) | база приложения |
| Mailpit | SMTP `localhost:1025`, веб-интерфейс `http://localhost:8025` | перехватчик писем — все письма платформы видны в браузере |

Остановить: `down` (данные сохранятся), полный сброс: `down -v`.

### Вариант Б — без контейнеров, нативно на Fedora

```bash
sudo dnf install postgresql-server postgresql-contrib
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

# ВАЖНО для Fedora: TCP-подключения по умолчанию идут через ident, который не работает.
# /var/lib/pgsql/data/pg_hba.conf: в строках host ... 127.0.0.1/32 и ::1/128
# заменить ident на scram-sha-256, затем:
sudo systemctl restart postgresql
sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'test';"
sudo -u postgres psql -c "CREATE DATABASE photo_booking;"

# Mailpit — один бинарь от вашего пользователя (root не нужен):
# https://github.com/axllent/mailpit/releases → linux-amd64.tar.gz
./mailpit                   # SMTP :1025, веб-интерфейс :8025
```

В обоих вариантах адреса одинаковые: база `localhost:5432`, письма `localhost:1025` /
интерфейс `localhost:8025`.

> Автотесты (`pnpm test:integration`) Docker не требуют вовсе — сами поднимают
> встроенный Postgres внутри себя. Node и pnpm на Fedora:
> `sudo dnf install nodejs npm && sudo npm i -g pnpm`.

## 4. Локальный запуск полного стека

```bash
# 1. инфраструктура (вариант А или Б из раздела 2)
docker compose -f docker-compose.dev.yml up -d

# 2. сервер (терминал 1)
cd server
cp .env.example .env
```

`.env` для тестов **без SMTP**:

```env
DATABASE_URL=postgres://postgres:test@localhost:5432/photo_booking
JWT_SECRET=тестовый-секрет-минимум-32-символа-длиной!!
WEB_ORIGIN=http://localhost:5173
PUBLIC_BASE_URL=http://localhost:3000
OPENAI_BASE_URL=http://localhost:3100/v1
OPENAI_API_KEY=mock
OPENAI_MODEL=gpt-4o-mini
```

(если подняли Mailpit — добавьте `SMTP_URL=smtp://localhost:1025`)

```bash
pnpm db:migrate                        # применит миграции к БД
pnpm studio:create --slug=kadr-studio  # студия-образец (или anna-vetrova — фотограф)
pnpm studio:invite --slug=kadr-studio  # печатает ссылку-приглашение ВЛАДЕЛЬЦУ
pnpm start                             # API на :3000 (+ воркер уведомлений внутри)
```

> После каждого обновления из git — `cd server && pnpm db:migrate`. Миграции
> только добавляются. Актуальные: `0011_addon_halls.sql` — белый список залов
> у допуслуг (`addons.hall_ids`), `0012_service_references.sql` — флаг
> «просить референсы» у услуги (`services.references_enabled`). Без них
> сохранение каталога и `studio:create` упадут на отсутствующей колонке.

```bash
# 3. мок ИИ (терминал 2)
pnpm mock:openai

# 4. фронтенд (терминал 3) — из корня репозитория
pnpm dev                               # :5173, /api автоматически проксируется на :3000
```

**Сделать себя платформ-админом** (создание студий, приглашения):

```bash
cd server && pnpm studio:invite --slug=kadr-studio --email=ваш@адрес
# активируйте приглашение, затем:
psql "$DATABASE_URL" -c "update users set is_platform_admin = true where email = 'ваш@адрес'"
```

## 6. РУЧНАЯ ПРИЁМКА — подробные сценарии

### 6.0. Как собирать и присылать результаты (скриншоты не нужны)

Всё, что нужно мне для починки, — **текст**. По каждому упавшему тесту присылайте:

1. **Номер теста и шаг**, на котором сломалось (например: «6.3, шаг 4»)
2. **Что вы делали** — одно предложение своими словами
3. **Что видели** — точный текст ошибки с экрана (скопируйте дословно)
4. **Ответ сервера**, если проблема в API. Как достать:
   - нажмите `F12` → вкладка **Network** → повторите действие → найдите запрос
     (красный = упавший) → кликните → справа **Response** → скопируйте JSON;
   - либо **Headers** → скопируйте строку Status (`409 Conflict` и т.п.)
5. **Хвост лога API** — из терминала, где запущен `pnpm start`, последние ~20 строк

Шаблон сообщения мне:

```
Тест: 6.4, шаг 2
Делал: открыл две вкладки, выбрал 12:00, отправил обе
Видел: первая — «Заявка отправлена», вторая — «Ошибка сервера»
Network: POST /api/public/studios/kadr-studio/bookings → 500
Response: {"error":{"code":"INTERNAL","message":"Внутренняя ошибка сервера"}}
Лог API: <хвост вывода терминала>
```

**Про токены (важно):** токен приглашения/записи — это случайная строка, которую
**генерирует сервер сам**. Вы ничего не придумываете и не вставляете руками:
команда `studio:invite` печатает **готовую ссылку целиком** — открываете её как
есть. Токен одноразовый и хранится в базе только хешем. Если ссылка уже
использована или истекла — просто запустите `studio:invite` снова: будет новая.

### 6.1. Онбординг владельца (без SMTP)

**Подготовка:** стек запущен (раздел 4). Ссылку даёт команда
`pnpm studio:invite --slug=<slug>` — **открываете её как есть, ничего не
генерируете**. Токен одноразовый: для повторного прохождения теста запустите
`studio:invite` ещё раз — будет новая ссылка.

1. Откройте напечатанную ссылку `http://localhost:5173/invite/<токен>` — целиком,
   вместе с токеном на конце
2. Введите пароль (минимум 8 символов) → «Создать аккаунт и войти»
3. Попробуйте ту же ссылку второй раз
4. Попробуйте ссылку с испорченным токеном (допишите пару символов в конце)

**Ожидание:**
- Шаг 2: попали в кабинет `/owner`, сверху имя студии, вкладки Заявки/Календарь/…
- Шаг 3: «Приглашение недействительно или истекло»
- Шаг 4: то же самое

**Если не так — прислать:** текст с экрана + саму ссылку (токен можно
заменить на `XXX`) + вывод `studio:invite`.

### 6.2. Кабинет наполняется: зал, услуга, специалисты

1. Кабинет → Настройки → «Залы и тарифы» → «+ Зал» → Сохранить; затем у зала
   «+ Фото зала» — загрузите 1–2 фото
2. «Услуги и пакеты» → «+ Услуга» → заполните: название, цена, длительность,
   предоплату, включите «нужен зал» → «Сохранить услугу»; в раскрытой карточке
   услуги загрузите обложку («Загрузить» у поля «Обложка услуги»)
3. «Специалисты» → «+ Специалист» → Сохранить → «Загрузить фото» у него
4. Настройки → смените название студии и акцентный цвет → «Сохранить настройки»

**Ожидание:**
- Каждое действие даёт спиннер на кнопке и зелёный тост «✓ …»
- После шага 4 цвет кнопок на витрине меняется **без перезагрузки** (вернитесь
  на вкладку витрины)
- На `/s/<ваш-slug>` в разделе аренды у зала фотолента, у услуги — обложка,
   в блоке «Пакеты съёмки» — фото; услуга с ценой и кнопкой «Записаться»

**Если не так — прислать:** шаг, текст из тоста, ответ запроса из
DevTools → Network (PUT/POST, вкладка Response).

### 6.3. Витрина и бронь с компьютера (10 мин)

1. Откройте `http://localhost:5173/s/<ваш-slug>` — прогуляйтесь по главной
2. «Записаться» → выберите дату (пн–сб, +3 дня от сегодня)
3. Посмотрите сетку времени: часть слотов перечёркнута
4. Выберите свободный слот → посмотрите блок «Итого»
5. Включите допуслугу → цена выросла
6. Заполните имя/телефон, галочку согласия → «Отправить заявку»
7. На экране успеха нажмите «Моя запись»
8. Там же «Добавить в календарь (.ics)» — откройте скачанный файл
9. Вторая вкладка с той же формой: отправьте заявку тем же временем ещё раз

**Ожидание:**
- Шаг 3: занятое перечёркнуто и не нажимается
- Шаг 4–5: цена = тариф × часы + допы, предоплата отдельной строкой
- Шаг 6: экран «Заявка отправлена» + секретная ссылка
- Шаг 7: таймлайн статусов, кнопка отмены активна
- Шаг 8: календарь открыл событие с правильным временем
- Шаг 9: вторая вкладка — «Это время только что заняли. Выберите другое»,
  в кабинете по-прежнему одна заявка

**Если не так — прислать:** номер шага + что было на экране + Response
запроса `bookings` из DevTools.

### 6.4. Двойная бронь двумя вкладками

1. Две вкладки формы, одно время, обе отправляют почти одновременно
2. Кабинет → список заявок на эту дату

**Ожидание:** одна «успех», вторая «время заняли»; в списке одна запись.

**Если не так:** прошли обе или упали обе — критичный баг: прислать ответы
**обоих** запросов из Network.

### 6.5. «Моя запись»: список записей, отмена в окне и вне окна

1. Создайте заявку №1 на дату +5 дней (далеко за пределами 48 ч)
2. «Моя запись» → убедитесь, что открылся **список записей** с этой бронью
3. «Открыть» → «Отменить запись» → подтвердите в диалоге
4. Проверьте слот: он снова свободен
5. Создайте заявку №2 на завтра, затем заявку №3 на +5 дней
6. «Моя запись» — в списке **обе активные**; отмените заявку №3 (внутри 48 ч
   нельзя — смотрите шаг 7 у заявки №2)
7. Заявка №2 (завтра): кнопка отмены

**Ожидание:**
- Шаг 2–3: список записей с этого устройства; отмена — через красивый диалог,
  статус «Отменена клиентом», таймлайн серый
- Шаг 4: слот снова активен на форме
- Шаг 6: обе записи видны, ссылки не теряются
- Шаг 7: кнопка неактивна, подпись «Отмена недоступна (48 ч)»

**Если не так — прислать:** время заявки, текст у кнопки отмены, ответ
запроса `cancel`.

### 6.6. Кабинет: жизненный цикл заявки (10 мин)

1. Заявки → найдите новую → «Действия»
2. Цепочка чипов: «Подтвердить» → «Предоплата получена» → внесите сумму в «Получено
   денег» → «Съёмка проведена» → «В обработке» → «Ссылка на материалы» = любой
   URL → «Завершена». Каждый шаг — спиннер на чипе и тост «✓ Статус обновлён»
3. «Перенести на»: смените дату/время → ОК
4. После каждого действия сверяйте клиентскую ссылку
5. Раздел «Сдачи»: после «Сдана» заявка уходит из «ждут сдачи»
6. Раздел «Статистика»: цифры меняются
7. «Экспорт CSV» → файл открывается в Excel без кракозябр

**Ожидание:**
- Статусы в кабинете и у клиента синхронны
- После «Сдана» у клиента блок «Готовые материалы» с кнопкой
- Перенос: старое время освободилось, новое занято

**Если не так — прислать:** какую кнопку нажали, ответ PATCH из Network.

### 6.7. Роли: сотрудник и менеджер (10 мин)

**Подготовка (теперь из UI):** Кабинет → вкладка **«Команда»** (видна только
владельцу) → «Пригласить» → email `e1@test.local`, роль «Сотрудник» →
«Пригласить». То же с `m1@test.local`, роль «Менеджер». Ссылки-приглашения
печатает сервер в консоли (или CLI `pnpm studio:invite`, как раньше).
Активируйте обе (второй браузер или инкогнито).

1. Сотрудник: какие вкладки видит? (только «Заявки» и «Календарь»)
2. Сотрудник: «Заявки» — видит список
3. Сотрудник: смотрит строки заявок — есть ли суммы?
4. Сотрудник: вручную открывает `/owner/team` и `/owner/settings`
5. Менеджер: все вкладки кроме «Команда»; меняет статус заявки
6. Владелец: «Команда» → удалить сотрудника

**Ожидание:**
- Шаг 1–3: у сотрудника скрыты Сдачи/Статистика/Портфолио/Настройки/Команда;
  суммы `0 ₽`; кнопки действий с тостом-ошибкой «Нет доступа» (403)
- Шаг 4: маршруты недоступны (вкладки отрисованы без них)
- Шаг 5: менеджер всё кроме «Команды»
- Шаг 6: участник удалён, его сессии отозваны (в его браузеле — «Требуется вход»)

**Если не так — прислать:** роль + что нажали + Status из Network.

### 6.19. Залы ↔ услуги: белые списки и автовыбор

1. Настройки → «Аренда зала» → «Доступные залы» → оставьте только «Белый зал»
   → Сохранить услугу
2. Витрина → форма аренды: в списке только «Белый зал»
3. Настройки → «Запись и правила» → выключите «Клиент выбирает зал» →
   Сохранить настройки
4. Витрина → форма аренды: списка нет, подпись «Зал подберётся автоматически»,
   под ней превью зала; бронь создаётся, в кабинете у заявки конкретный зал
5. Верните выбор зала; выключите «Клиент выбирает специалиста» → бронь без
   выбора человека — сервер назначил свободного

**Ожидание:** во всех режимах двойная бронь невозможна; смена услуги
сбрасывает недоступный зал.

**Если не так — прислать:** услугу, режим переключателей, Response
`availability` и `bookings` из Network.

### 6.20. Команда на витрине и «Мои записи»

1. Настройки → «Команда на витрине» вкл → сохраните → на главной блок «Кто
   будет с вами»; у специалиста без фото — инициалы
2. У Марка «Скрыт из команды» → блок на витрине без него, в форме записи он
   остался
3. «Отключить» у специалиста → пропал и из формы записи
4. Сделайте две брони подряд → «Моя запись» показывает обе, ссылки живы

**Ожидание:** все переключатели мгновенно влияют на витрину после
«Сохранить настройки».

### 6.21. Допуслуги внутри услуг

1. Настройки → Услуги → раскрыть «Портретная съёмка» → «Допуслуги услуги (N)»
2. «+ Допуслуга» → впишите название/цену → «Сохранить» (кнопкой в строке допа)
3. Витрина → форма записи портрета: доп появился в «Дополнительно»
4. «Love story» → допа нет; ✕ у допа в портрете → пропал (если никем больше не используется — удалён из базы)

**Ожидание:** отдельного раздела «Допуслуги» в настройках больше нет; цена заявки считается сервером, чужие допы в запросе отбрасываются. Привязка допа к конкретным залам — тест 6.28.

### 6.22. Специалисты услуги и карточки выбора

1. Услуга → «нужен специалист» → блок «Специалисты услуги» появляется сразу; отметьте только Анну → Сохранить
2. Витрина → форма записи: карточки специалистов с фото (Анна — есть, Марка нет)
3. Заявка «Любой свободный» → в кабинете у заявки Анна
4. Снимите галку «Клиент выбирает специалиста» → вместо карточек подсказка про автоподбор

**Ожидание:** сервер отклоняет чужого специалиста («Специалист недоступен для этой услуги»); один разрешённый специалист → строка «Съёмку проведёт: …».

### 6.23. Графики специалистов

1. Настройки → Специалисты → у Анны «График специалиста — как у студии» → «Задать свой график» → пн 12:00–14:00, остальные выходные → «Сохранить график»
2. Витрина → форма портрета на понедельник: слоты только 12:00–14:00 (12:30 при буферах)
3. «Как у студии» → слоты вернулись по графику студии

**Ожидание:** слоты specialist-а считаются по его окну в каждой задействованной дате; «Любой свободный» ищет только среди тех, чей график покрывает слот.

### 6.24. «Весь день»: цена по окнам зала

1. Услуга с «весь день» + почасовая (создайте или включите на «Аренда зала»)
2. Витрина → форма → дата → карточка **«Весь день — 10:00–21:00 · 11 ч зала · сумма»**
3. Сумма = часы окна × тарифы (будни/выходные, день/вечер — почасово). Сравните с тарифами зала вручную
4. Заброньируйте → в кабинете конец заявки = закрытие зала, занято всё окно

**Ожидание:** слот-кнопки для fullDay нет — только карточка; цена и конец считаются сервером по графику студии (клиент длительность не шлёт).

### 6.25. Удаление залов и специалистов

1. Настройки → Специалисты → «Удалить» у тестового → диалог с описанием → подтвердить
2. Настройки → Залы → «Удалить» тестовый зал → подтвердить
3. Бронь, где был этот специалист/зал, — в кабинете: заявка жива, привязка пуста
4. Слоты, которые он блокировал, — снова свободны

**Ожидание:** «Отключить» — мягко (вернуть можно), «Удалить» — из каталога навсегда;
брони и деньги не страдают; в тостах подтверждения.

### 6.26. Ставка специалиста (почасовая услуга с человеком)

1. Настройки → Специалисты → Анне «Ставка, ₽/час» = 1500 → Сохранить
2. Создай почасовую услугу «нужен специалист» + «нужен зал» + белый список Анны
   (без зала — тоже допустимо, см. 6.35)
3. Витрина → форма: карточка Анны с подписью «+1 500 ₽/час», «Итого» — **две строки**:
   «зал · часы × тариф» и «Специалист: Анна — ставка × часы»
4. У «Аренды зала» включите «нужен специалист» → появился белый список
   специалистов; в почасовой аренде «Итого» добавляет строку
   «Специалист: … — ставка × часы»

**Ожидание:** ставка умножается на фактические часы брони (весь день — по окнам);
фикс-услуги ставку не добавляют; сервер считает сам — клиентская оценка не источник истины.
Без зала почасовая съёмка разрешена, если есть специалист; все ставки команды
суммируются (6.35).

### 6.27. Услуги аренды и залы на главной (7 мин)

1. «Залы и тарифы»: минимум 2 активных зала с фото и разными тарифами
2. «Услуги и пакеты»: «Аренда зала» (тип «Аренда зала», нужен зал, без
   специалиста) и «Аренда со специалистом» (тот же тип, нужен зал + нужен
   специалист, отметьте специалистов)
3. Главная, блок «Услуги и аренда»: среди карточек услуг есть карточка
   «Аренда зала». Клик по ней → форма записи с выбранной услугой аренды; URL
   содержит `mode=rental&service=…`
4. Ниже отдельный блок «Аренда зала» с карточками залов: два фото зала,
   название, вместимость и полный прайс (будни/выходные, день/вечер). Кнопка
   «Арендовать зал»
5. Клик по карточке зала (не по кнопке) → попап с подробностями: все фото
   (клик — на весь экран), вместимость, полный прайс и кнопки услуг аренды
6. Кнопка «Арендовать зал» при одной подходящей услуге → форма записи с уже
   выбранным залом; URL содержит `mode=rental&service=…&hall=…`. Если услуг
   несколько — кнопка открывает попап выбора
7. В «Аренде зала» оставьте в «Доступные залы» только первый зал: у второго
   появится «Бронь пока недоступна», в его попапе останется только
   «Аренда со специалистом» (если она этот зал покрывает)
8. На тестовой студии удалите все услуги типа «Аренда зала»: карточка услуги
   исчезает, залы на главной остаются с фото и прайсом, кнопок брони нет; в
   «Залы и тарифы» — предупреждение «Залы без услуги аренды». Автосоздания
   услуги быть не должно

**Ожидание:** услуга аренды видна в блоке услуг и ведёт в форму; залы — одна
сетка компактных карточек с парой фото и прайсом, подробности — в попапе; без
услуги остаётся честная информация без мёртвых кнопок.

**Если не так — прислать:** зал, какая услуга выбрана, Response `availability`
и `bookings`, скрин не нужен.

### 6.28. Допуслуги и залы (5 мин)

1. Услуга с залом → «Допуслуги услуги» → у допа по умолчанию радио «Во всех
   залах»
2. «Только в выбранных» → отметьте «Белый зал» → «Сохранить» у допа
3. Витрина → выберите «Белый зал»: доп есть в «Дополнительно» и в «Итого»;
   выберите второй зал — допа нет
4. Отметьте доп, затем смените зал: галочка допа снимается, в заявку он не
   попадает
5. Снимите все залы → радио вернулось «Во всех залах», доп снова доступен везде
6. Услуга без зала (выезд): доп с привязкой к залам не показывается
7. Услуга без привязанных допов: блок «Дополнительно» пуст, допы других услуг
   не появляются

**Ожидание:** фильтр по услуге И залу; в кабинете сумма совпадает с «Итого»;
чужой/устаревший доп сервер не считает.

**Если не так — прислать:** услугу, зал, какие допы отмечены, Response
`bookings` и сумму из кабинета.

### 6.29. Предпросмотр фото до загрузки (5 мин)

1. «Специалисты» → «Загрузить фото»: открылся макет карточки; для файла меньше
   400×400 — предупреждение; «Отмена» — фото не загрузилось
2. «Залы и тарифы» → «+ Фото зала»: макет карточки/попапа; меньше 1024×768 —
   предупреждение
3. «Услуги и пакеты» → фото услуги: макет карточки; меньше 1024×768 —
   предупреждение
4. «Портфолио»: выберите файл → «Добавить карточку» → предпросмотр → «Выбрать
   другое» (открывается выбор файла, макет обновляется) → «Загрузить»
5. У готовой работы «Заменить фото» → предпросмотр → замена

**Ожидание:** фото уходит на сервер только после подтверждения; предпросмотр
использует реальные стили витрины, а не абстрактный прямоугольник.

### 6.30. Push-напоминания (опционально, нужен HTTPS)

Требуются `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY` в `server/.env`; ключи:
`cd server && node -e "console.log(require('web-push').generateVAPIDKeys())"`.
В демо-режиме кнопка не показывается — нужен полный стек и HTTPS (туннель).

1. Оформите бронь на витрине → на экране успеха «Включить напоминания об этой
   записи» → разрешите уведомления
2. Проверьте подписку:
   `psql "$DATABASE_URL" -c "select count(*) from push_subscriptions"`
3. Ускорьте напоминание:
   `psql "$DATABASE_URL" -c "update notify_outbox set next_attempt_at = now() where channel='reminder_client' and status='pending'"`
4. Дождитесь воркера (до минуты) → должно прийти push-уведомление

**Ожидание:** push с иконкой студии, клик открывает витрину `/s/<slug>`; без
VAPID кнопки нет, ошибок на витрине нет.

### 6.31. Референсы: только там, где нужны (4 мин)

1. Настройки → Услуги → «Аренда зала»: у «просить референсы» галочка снята
   автоматически (услуга без специалиста)
2. Услуга со специалистом: галочка включена автоматически; снимите и включите
   снова — решение фиксируется явно
3. Витрина → аренда зала: блока «Референсы» нет; съёмка: блок есть, можно
   выбрать до 5 изображений
4. В форме съёмки выберите референсы, затем смените услугу на аренду: блок
   исчез, в заявке нет строки «Референсы»
5. Явно включите референсы для аренды → блок появился; выключите для съёмки →
   пропал

**Ожидание:** блок управляется флагом услуги (`referencesEnabled`); без флага
работает авто: съёмка со специалистом — да, чистая аренда — нет; при смене
услуги выбранные файлы не попадают в заявку.

**Если не так — прислать:** услугу, состояние галочки, Response `bookings` и
строку «Референсы» в кабинете.

### 6.32. Размер карточек услуг и залов (4 мин)

1. Настройки → «Внешний вид»: есть две независимые настройки — «Размер карточек
   услуг» и «Размер карточек залов»
2. Для услуг выберите «Компактные» и сохраните: на главной и в «Услугах»
   карточки услуг стали уже, в ряд помещается больше
3. Для услуг выберите «Крупные»: карточки услуг шире и просторнее
4. Для залов выберите «Компактные»: карточки в «Аренде зала» на главной и в
   «Аренде студии» стали меньше
5. Для залов выберите «Крупные»: карточки залов шире; «Обычные» — исходный вид
6. Перезагрузите витрину — оба размера сохранились и не влияют друг на друга
7. Проверьте на телефоне: карточки в одну колонку, без горизонтальной прокрутки

**Ожидание:** настройки независимо меняют сетку карточек услуг и сетку карточек
залов; выбор хранится в настройках студии.

**Если не так — прислать:** выбранный размер, на какой странице не применился,
и ширина окна браузера.

### 6.33. Тип услуги и ресурсы (2 мин)

1. Настройки → Услуги → карточка услуги → «Тип записи»: варианты называются
   «Съёмка» и «Аренда зала (зал обязателен)»
2. Под селектором подсказка: оба типа показываются в блоке «Услуги и аренда»,
   залы — отдельным блоком ниже
3. Фикс-услуга, снимите и «нужен специалист», и «нужен зал»: появляется
   предупреждение «Без зала и специалиста услугу оказать нельзя»
4. Включите зал или специалиста — предупреждение исчезло

**Ожидание:** название типа не обещает наличие специалиста; настройки ресурсов
остаются в карточке услуги, а невозможная комбинация подсвечивается.

**Если не так — прислать:** тип услуги, состояние галочек «зал»/«специалист» и
текст предупреждения.

### 6.34. Белый список залов услуги (3 мин)

1. Настройки → Услуги → «Аренда зала» → блок «Доступные залы»
2. Выберите «Только в выбранных». Первый зал уже отмечен — снимите его нельзя,
   пока не отметите второй
3. Оставьте только «Лофт-зону», нажмите «Сохранить услугу»
4. Откройте витрину: у «Белого зала» должно быть «Бронь пока недоступна», у
   «Лофт-зоны» — «Арендовать зал»
5. В форме аренды должен быть только «Лофт-зона». Ссылка с `hall=` на чужой зал
   не должна отправлять его в заявку
6. Вернитесь в настройки, выберите «Все залы», сохраните — аренда снова доступна
   для обоих залов
7. Попробуйте ручную заявку на чужой зал через API — сервер должен ответить
   «Зал недоступен для этой услуги»

**Ожидание:** белый список залов соблюдается и на витрине, и в форме записи, и
в ручной заявке. Пустой выбор не сохраняется: он означал бы «все залы».

**Если не так — прислать:** какой зал остался доступен, состояние радиокнопок
«Все залы»/«Только в выбранных» и Response из DevTools.

### 6.35. Почасовая съёмка без зала и услуга-команда (5 мин)

1. Настройки → Специалисты: у Анны и Марка заполнена «Ставка, ₽/час»
2. Создайте почасовую услугу «Час без зала»: тип «Съёмка», «нужен специалист»
   включён, «нужен зал» снят, в белом списке — Анна
3. Витрина → карточка «Час без зала»: нет выбора зала, есть слоты; в «Итого»
   ровно одна строка «Специалист: Анна — ставка × часы», зала нет
4. Оформите бронь: в заявке `hallId=null`, специалист Анна, сумма равна
   ставке × часы
5. Создайте услугу «Команда»: тоже почасовая съёмка без зала, включите
   «услугу выполняют все отмеченные специалисты» и отметьте Анну и Марка
6. Витрина → «Команда»: клиент не выбирает специалиста; в «Итого» две строки
   специалистов, сумма = (ставка Анны + ставка Марка) × часы
7. Оформите бронь: в «Заявках» видны оба специалиста, в БД
   `bookings.specialist_ids` = оба id, в `booking_resources` — две блокировки
8. Снимите одного из специалистов с услуги-команды или оставьте пустой состав:
   слотов быть не должно, API отвечает ошибкой настроек

**Ожидание:** почасовая съёмка без зала допустима только при наличии
специалиста; ставки суммируются по всем участникам, а не берётся минимальная.
Фикс-пакеты ставки специалистов не добавляют. Аренда зала по-прежнему всегда
требует зал.

**Если не так — прислать:** тип услуги, состояние «нужен зал»/«команда»,
состав специалистов, сумму в «Итого» и Response из DevTools.

### 6.36. Регрессии аудита 18.11.2026 (15 мин)

Проверяем исправления, которые не видны на обычном happy-path.

1. **Каталог двух студий.** Создайте вторую студию с теми же id услуг/залов/
   специалистов (или импортируйте tenant.json с повторяющимися id). Обе студии
   должны сохраниться и открываться; ошибки `_bt_check_unique` быть не должно.
2. **Настройки владельца.** В `PUT /settings` попробуйте подменить `slug` или
   `status` (например, через DevTools). Ответ 200, но в БД и в ответе остаются
   прежние значения; плашка «ОБРАЗЕЦ»/noindex не снимается.
3. **Права сотрудника.** Войдите сотрудником без `finance:read` и откройте
   `GET /api/owner/studios/:slug`: `calendarToken` должен быть `null`.
4. **Отзыв доступа.** Деактивируйте пользователя (`is_active=false`) и нажмите
   «Обновить» в другой вкладке с протухшим access-token: refresh → 401, без
   новой сессии.
5. **Валидация каталога.** POST услуги с несуществующим `defaultHallId`,
   `hallIds`/`specialistIds`/`addonIds` или с `allSpecialistsRequired=true` и
   пустым составом → 400 `VALIDATION`. Кривой график (открытие 21:00,
   закрытие 10:00) → 400. Закрытый период с `dateTo < dateFrom` → 400.
6. **Ручная бронь.** В «Заявках» создайте заявку на несколько дней и на
   «весь день»; проверьте мин-дату, поле «Дней», цену (для многодневной аренды —
   полные окна всех дней) и перенос: для allDay/многодневной достаточно даты,
   занятый день предупреждает.
   Сотрудник (`employee`) не видит кнопку «Действия».
7. **Список заявок.** Смена таймзоны студии меняет границы дня в фильтре
   `dateFrom/dateTo`; заявки на границе суток не теряются и не дублируются.
8. **Уведомления.** Остановите SMTP, создайте 2–3 заявки, запустите сервер
   снова: письма не дублируются, `notify_outbox` не застревает в `processing`;
   после восстановления SMTP очередь доходит. Push-текст не содержит телефона.
9. **Помощник.** Запрос с несуществующим id услуги → понятная ошибка со
   списком валидных id, без подстановки первой услуги. При 429/401 от OpenAI
   и пустом ответе — сообщение «недоступен», не пустой пузырь.
10. **Команда.** Раздел «Команда» показывает участников и приглашения с живыми
    датами (не `Invalid Date`).
11. **Каталог новой студии.** `pnpm studio:create --slug=...` переносит график
    специалистов, ставки, фото залов, `hallIds`/`specialistIds` услуг и
    `photo_url` услуги.
12. **Аренда.** Выключите `modes.rental` в настройках: блок аренды исчезает с
    главной и из услуг, форма записи не открывается в rental-режиме.
13. **Фото.** Замените фото специалиста/зала/услуги/работы портфолио: старый
    файл исчезает из `server/uploads`, новый открывается; общие файлы не
    удаляются.
14. **Эксплуатация.** `GET /api/health` → `{"ok":true}` (при остановленной БД —
    503). OPTIONS с Origin → `Access-Control-Max-Age: 86400`. `/uploads/...`
    отдаётся с `Cache-Control: max-age=2592000, immutable`. SIGTERM завершает
    API без обрыва текущих запросов; при `TRUST_PROXY=true` rate-limit видит
    реальный IP из `X-Forwarded-For`.
15. **iCal.** 61-й запрос за минуту с одного IP → 429.
16. **Ошибка UI.** Временно бросьте исключение в компоненте: вместо белого
    экрана — карточка «Что-то сломалось» с кнопкой «На главную».

**Ожидание:** все пункты проходят без ручных правок БД; старые демо-сценарии
(6.1–6.35) остаются зелёными.

**Если не так — прислать:** номер пункта, шаги, текст с экрана, Response из
DevTools и хвост лога API.

### 6.37. Этап Y — ночные смены, референсы, тарификация окон (15 мин)

1. **Ночная смена.** В настройках студии поставьте, например, понедельник
   22:00–06:00. Сохраните — появится подсказка «до следующего дня». На витрине
   в этот день слоты идут с 22:00 до 05:00 (для часа), подпись графика —
   «(до следующего дня)».
2. **Бронь ночи.** Забронируйте слот 22:00 на 8 часов: в кабинете заявка должна
   занимать время до 06:00 следующего дня, а в цене — часы после полуночи по
   тарифу уже следующего дня.
3. **Многодневная аренда.** Создайте почасовую аренду с `multiDayMax > 1`, выберите
   2 дня. В форме нет поля «Часов», в «Итого» — полные окна обоих дней (даже если
   клиент пришёл на пару часов).
4. **Референсы.** Отправьте заявку с 1–5 изображениями. В кабинете откройте
   карточку заявки → «Референсы»: миниатюры открываются. Нажмите «Удалить данные
   клиента» — список референсов пустеет, файлы из `server/uploads` исчезают.
5. **Notify.** Остановите SMTP, создайте заявку и перезапустите API: строка не
   должна навсегда остаться в `processing`; после восстановления SMTP письмо
   доходит, дублей нет.

### 6.38. Этап Z — ночная витрина, локаль, честные референсы (15 мин)

1. **Ночные слоты витрины.** В настройках студии поставьте понедельник
   22:00–06:00. В форме записи на этот день сетка слотов должна содержать
   разделитель «ночь след. дня ↓» перед слотами после полуночи. Выберите слот
   после полуночи — появится предупреждение «Бронь закончится на следующие
   сутки».
2. **Конец брони.** На экране успеха и в «Моей записи» время показано как
   «22:00–06:00 след. дня», а не только время начала.
3. **Русские даты.** На витрине и в кабинете даты читаются по-русски:
   «19 ноября 2026, четверг», без английских месяцев и дней недели.
4. **Календарь кабинета.** Ночная бронь видна в обеих ячейках: в день начала и
   в следующем дне. Перенос «весь день» с ночного дня (22:00–06:00) на дневной
   даёт конец 21:00 по графику, а не «старт + 8 часов».
5. **CSV.** Выгрузка заявок содержит колонку «До» с окончанием, включая
   «06:00 след. дня» для ночных броней.
6. **Анонимизация и референсы.** После «Удалить данные клиента» кнопка
   «Референсы: N шт.» исчезает из карточки, а раскрытый блок пуст — без битых
   картинок.
7. **Тост ночной смены.** В настройках при смене 22:00–06:00 появляется жёлтый
   тост с «ℹ», а не зелёная галочка успеха.

## 7. Ручная приёмка Docker: зачем он тут, чем поможет при деплое и сколько учить

**Где используется:** ровно в одном месте — `docker-compose.dev.yml` поднимает
тестовые Postgres + Mailpit для ручной проверки. Фронтенд и сервер запускаются
**нативно через Node** — Dockerfile в проекте нет. На проде Docker не нужен:
Postgres пакетом, API — systemd-сервисом.

**Чем поможет при деплое (потом):** инфраструктура описана текстом — перенос на
новый сервер это «скопировал compose, up -d»; тестовая база стирается одной
командой; одинаковая среда у вас и в будущем CI.

**Сколько учить:** уровня «три команды» — `up -d`, `down`, `logs` — плюс четыре
слова: образ, контейнер, том, порт. Один вечер. На Fedora вместо Docker есть
**Podman** (без демона и root) — команды взаимозаменяемы, compose-файл тот же.

**Вывод:** сейчас можно жить без него (вариант Б из раздела 2). Учить — когда
заворачиваете прод в контейнеры или добавляете CI; порог входа — один вечер.

## 8. Деплой на VPS (Fedora Server)

### 8.1 Минимальные характеристики сервера

Продукт лёгкий: статический фронт + один Node-процесс + Postgres. Тяжёлого нет —
фото хранятся на диске (не в БД), ИИ — сетевой вызов, основная нагрузка — редкие
всплески загрузки фото (multer держит до ~30 МБ в памяти).

| Ресурс | Минимум (впритык) | Комфорт |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU |
| RAM | 1 ГБ + swap 1 ГБ (ОС ~200 МБ + Postgres ~150–300 МБ + Node ~100–150 МБ) | 2 ГБ |
| Диск | 10 ГБ NVMe | 20 ГБ NVMe (растёт от фото: ~1 МБ за фото в трёх размерах) |
| ОС | любой Linux x86_64: Fedora Server / Ubuntu 22+ / Debian 12 / Alma, Rocky | — |
| Софт | Node.js 20+, pnpm, PostgreSQL 15+, nginx, certbot; домен с A-записью | — |

Трафик: сотни посетителей/день для типового тарифа — незаметно. Ориентир цен
РФ-хостеров (Timeweb Cloud, Selectel, Reg.ru, Beget): 1 vCPU / 1–2 ГБ NVMe —
порядка 300–700 ₽/мес (актуальные цены смотрите на сайтах).

**Триггеры масштабирования** (когда делить/усиливать): 50+ активных студий,
устойчивая загрузка CPU > 50%, Postgres съедает > 70% RAM → БД на отдельный
сервер и/или +vCPU. До этого — всё на одном VPS, база на localhost.

### 8.2 Окружение и готовые файлы

Готовые файлы — `server/deploy/` (nginx + systemd). Специфика Fedora/RHEL:

```bash
sudo dnf install nginx certbot python3-certbot-nginx
# SELinux: разрешить nginx ходить на локальный :3000 и читать dist/
sudo setsebool -P httpd_can_network_connect on
sudo dnf install policycoreutils-python-utils
sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/app/dist(/.*)?"
sudo restorecon -R /var/www/app/dist
# firewall: открыть 80/443
sudo firewall-cmd --permanent --add-service=http --add-service=https && sudo firewall-cmd --reload
```

В `server/deploy/photo-booking.service` пользователь `booking` (в Fedora нет
`www-data`): `sudo useradd -r booking` и `chown -R booking:booking uploads`.

Почта на VPS: реальный SMTP-провайдер (UniOne / SendPulse PAYG / Mailganer);
ИИ: реальный `OPENAI_API_KEY`. Сброс пароля: SMTP или `pnpm user:reset`.
