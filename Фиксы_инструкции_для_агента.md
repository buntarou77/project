### 🔴 П1 — Референсы клиентов доступны по прямой ссылке без авторизации

**Суть.** `server/src/app.ts:56` раздаёт весь `uploads/` статикой без проверки сессии, включая `<studioId>/references/<uuid>.jpg` — приватные фото клиентов. Загрузка и списки защищены, а сам файл — нет. При этом UI обещает (`Requests.tsx:485`): «Файлы приватные: ссылка работает только внутри кабинета». URL попадает в `<img src>`, кэш браузера, историю, логи прокси. Неугадываемый UUID — не защита для персональных данных (ФЗ-152, на который сам проект ссылается в комментарии к `anonymizeClient`).

**Стратегия фикса (без миграций).** Файлы референсов перестают раздаваться статикой; отдаём их только через два авторизованных роута — кабинет (`requireStudioAccess`) и витрина (токен брони). Прямые URL из API убираем.

#### Шаг 1. Сервер: роут отдачи файла для кабинета

**Файл `server/src/routes/owner.ts`** — после существующего `GET .../bookings/:id/references` (строка 331):

```ts
// П1: файл референса отдаётся только с доступом к студии (не статикой)
ownerRouter.get(
  '/studios/:slug/bookings/:id/references/:refId/file',
  requireStudioAccess('bookings:read'),
  asyncHandler(async (req: StudioRequest, res) => {
    const r = await query<{ file_path: string; mime: string }>(
      `select file_path, mime from booking_references
       where id = $1 and booking_id = $2 and studio_id = $3`,
      [req.params.refId, req.params.id, req.studio!.id]
    )
    if (r.rows.length === 0) throw notFound('Файл не найден')
    const abs = path.resolve(config.UPLOADS_DIR, r.rows[0].file_path)
    // страховка от path traversal: не выходим за пределы UPLOADS_DIR
    if (!abs.startsWith(path.resolve(config.UPLOADS_DIR) + path.sep)) throw notFound('Файл не найден')
    res.setHeader('Content-Type', r.rows[0].mime)
    res.setHeader('Cache-Control', 'private, max-age=0, no-store') // персональные данные не кэшируем
    res.sendFile(abs)
  })
)
```

`path`, `config`, `query`, `notFound`, `asyncHandler`, `requireStudioAccess` в этом файле уже импортированы.

### 🟠 П2 — Напоминание клиенту не синхронизируется при переносе/закрытии брони владельцем

**Суть.** `reminder_client` создаётся при бронировании с `sendAt = старт − 24ч` (`bookings.ts:496`); клиентская отмена удаляет pending-строку (`bookings.ts:562`), а `updateBooking` — нет. Итог: владелец перенёс бронь с пятницы на вторник → в четверг клиент получает push «съёмка пятница» и приходит не тогда; `rejected`/`no_show`/`completed` не гасят напоминание; перенос не двигает `next_attempt_at`.

**Как чинить.** Файл `server/src/services/bookings.ts`, функция `updateBooking` (строка ~668). Вставка — внутри `tx(...)`, сразу ПОСЛЕ блока пересоздания `booking_resources` (после `} else if (closing) {...}`, перед `return mapBooking(...)`). В этой точке уже известны `id`, `startsAtMs`, `closing`, `resize`, `row.service_name`, `studio`:

```ts
// П2: напоминание клиенту живёт по актуальному времени брони.
// closing — гасим; resize — пересоздаём с новым sendAt и текстом.
if (closing) {
  await c.query(
    `delete from notify_outbox where booking_id = $1 and channel = 'reminder_client' and status in ('pending','processing')`,
    [id]
  )
} else if (resize) {
  await c.query(
    `delete from notify_outbox where booking_id = $1 and channel = 'reminder_client' and status in ('pending','processing')`,
    [id]
  )
  const remindAtMs = startsAtMs - 24 * 3_600_000
  if (remindAtMs > Date.now() && newStatus === 'confirmed') {
    await c.query(
      `insert into notify_outbox (studio_id, booking_id, channel, payload, next_attempt_at)
       values ($1, $2, 'reminder_client', $3, $4)`,
      [
        studio.id,
        id,
        JSON.stringify({
          title: 'Напоминание о записи',
          body: `${row.service_name}, ${utcToZonedDate(studio.settings.tz, startsAtMs)} ${utcToZonedTime(studio.settings.tz, startsAtMs)}`,
          icon: `/s/${studio.slug}/icons/icon-192.png`,
          url: `/s/${studio.slug}`,
        }),
        new Date(remindAtMs),
      ]
    )
  }
}
```

Детали:
- Условие `newStatus === 'confirmed'`: напоминание имеет смысл только для подтверждённой брони. Если в продукте решили напоминать и про `new` — уберите условие осознанно (тогда и в `createPublicBooking` логика должна совпасть — там напоминание создаётся для любой брони; для консистентности можно синхронизировать оба места в одну сторону).
- Вставка именно в транзакции: если перенос откатится по 23P01, напоминание не должно измениться.
- Импорты `utcToZonedDate`, `utcToZonedTime` уже есть вверху файла.

**Тест** (`server/tests/api.test.ts`, рядом с существующими update-тестами):

```ts
it('P2: перенос пересоздаёт напоминание, закрытие — гасит', async () => {
  // 1) создать бронь через публичный API (autoConfirm-услуга) — reminder_client в outbox
  // 2) PATCH: startsAtMs + 7 дней
  //    → старой строки нет; новая с next_attempt_at ≈ новый старт − 24ч
  // 3) PATCH: status 'rejected'
  //    → строк reminder_client нет
})
```

**Как проверить руками:** в демо не воспроизвести (outbox только в express-режиме) — интеграционный тест либо тестовый стенд: создать бронь на завтра+, перенести в кабинете, смотреть `notify_outbox`.

**Объём:** 1 час + тест.

### 🟠 П3 — Перенос многодневной брони на неделю с закрытым хвостом молча урезает её

**Суть.** `move()` в `Requests.tsx:283` проверяет только «все дни закрыты» (`fdw.windows.length === 0`). Проверено запуском ядра: график «вс открыт, пн закрыт», `dayCount=2`, перенос на воскресенье → `buildFullDayWindows` вернёт 1 окно из 2, сервер примет, бронь тихо станет однодневной — клиент заплатил за два дня, занят один. Обратный случай: перенос с дневного окна (11 ч) на ночное (8 ч) уменьшает занимаемое время, цена не пересчитывается (П7).

**Как чинить — фронт (основной фикс).** Файл `src/owner/Requests.tsx`, функция `move()`:

```ts
// ДО
if (fdw.windows.length === 0) {
  toast(`В ${date} студия закрыта — выберите другой день`, 'err')
  return
}

// ПОСЛЕ: каждое из dayCount дней должно быть открыто; меньше окон —
// бронь молча урезалась бы, запрещаем
const expectedDays = b.dayCount > 1 ? b.dayCount : 1
if (fdw.windows.length === 0) {
  toast(`В ${date} студия закрыта — выберите другой день`, 'err')
  return
}
if (fdw.windows.length !== expectedDays) {
  toast(`Среди выбранных дней есть закрытые — перенос невозможен. Нужны все ${expectedDays} дн. подряд открытыми`, 'err')
  return
}
```

**Как чинить — сервер (второй слой защиты, чтобы фикс не зависел от фронтенда).** Файл `server/src/services/bookings.ts`, `updateBooking`, внутри блока валидации `(resize || reopen) && !closing && row.service_id` — после `getSlots`-проверки добавить:

```ts
// П3: full-day/многодневная бронь обязана покрыть все свои дни:
// часть дней закрыта → бронь молча урежется, запрещаем на сервере
if ((row.all_day || row.day_count > 1) && resize) {
  const fdw = buildFullDayWindows(
    studio.settings.schedule,
    studio.settings.tz,
    startsAtMs,
    row.day_count > 1 ? row.day_count : 1
  )
  if (fdw.windows.length !== (row.day_count > 1 ? row.day_count : 1)) {
    throw badRequest('В выбранных днях есть закрытые — перенос невозможен')
  }
}
```

`buildFullDayWindows` уже импортирована вверху файла (используется в `createPublicBooking`) — просто вызвать.

**Тест.** Интеграционный в `api.test.ts`: создать 2-дневную full-day бронь, PATCH с переносом на дату, где второй день закрыт в расписании → 400. UI-сценарий дописать в TESTING 6.38: «перенос 2-дневной брони на вс при закрытом пн → красный тост, бронь не изменилась».

**Как проверить руками:** демо, услуга «полный день» на 2 дня; в настройках закрыть понедельник; в заявках перенести бронь на воскресенье — до фикса уедет молча, после — тост.

**Объём:** 30 минут + тест.

### 🟡 П6 — Календарь кабинета не видит ночную бронь, начавшуюся за день до диапазона

**Суть.** `Calendar.tsx:48` запрашивает `dateFrom: range.from`; сервер фильтрует `starts_at >= from`. Ночная бронь пн 22:00–вт 06:00 при просмотре недели «вт–вс» не попадёт в выборку, хотя занимает вторник до 06:00. Исполнитель Z оставил это «на потом» — чинится на фронте.

**Как чинить.** Файл `src/owner/Calendar.tsx`. `shiftDate` уже есть в файле (строка 10). Две правки:

```ts
// ДО
const { data, isLoading } = useQuery({
  queryKey: ['owner-cal', slug, range.from, range.to],
  queryFn: () => be.ownerBookings(slug, { dateFrom: range.from, dateTo: range.to }),
})

// ПОСЛЕ: −1 день — ночная бронь, начавшаяся накануне, занимает первый день
// диапазона; byDate (Z3) разложит её по дням занятия корректно
const { data, isLoading } = useQuery({
  queryKey: ['owner-cal', slug, shiftDate(range.from, -1), range.to],
  queryFn: () => be.ownerBookings(slug, { dateFrom: shiftDate(range.from, -1), dateTo: range.to }),

```

Ключ кэша меняется синхронно с запросом, чтобы разные диапазоны не склеились в react-query.
