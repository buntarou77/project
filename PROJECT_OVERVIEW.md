# PHOTO BOOKING PLATFORM — полное описание проекта

Документ для разработчика, который раньше работал с обычными API (Express / FastAPI /
REST) и впервые видит Supabase, и для менеджера, запускающего продукт в продакшн.
Порядок чтения разработчиком: разделы 1 → 2 → 3 → дальше по необходимости.
Менеджеру: 1, 2, 12 и 13.

---

## 1. Что такое tenant и зачем это вообще нужно

**Tenant (тенант, «арендатор») — одна студия/фотограф на нашей платформе.**

Мы делаем НЕ отдельный сайт для каждого клиента. Мы делаем **один продукт, в котором
живут много клиентов**, — как жилой дом, где одна инфраструктура (фундамент, вода,
электричество = наш код, база, хостинг), но много квартир, и каждая семья обустраивает
свою квартиру сама (название, фото, цены, график = настройки тенанта).

Практически:

- tenant идентифицируется **slug** — коротким именем в адресе: `/s/kadr-studio/`.
  Это «номер квартиры»;
- у каждого тенанта свои: витрина, портфолио, услуги, цены, залы, специалисты,
  график, акцентный цвет, владелец, заявки;
- **общие у всех**: код приложения, база данных (одна на всех!), хостинг, движок
  расчёта цен и свободного времени.

**Зачем так:** если бы каждый клиент получал свой сайт, то 100 клиентов = 100 копий
кода, которые надо отдельно обновлять и чинить. В мультитенантной модели мы чиним баг
**один раз** — и у всех сразу. Добавили новую фичу — получила вся платформа. Именно
поэтому:

- все данные в таблицах помечены `studioId` («в какой квартире лежит вещь»);
- база сама не даёт владельцу одной студии увидеть данные другой (об этом — раздел 6);
- нового клиента подключаем **без написания кода** — только файл настроек (раздел 3,
  папка `tenants/`).

Файл `tenants/<slug>/tenant.json` — это «анкета новой квартиры»: один JSON со всеми
стартовыми данными студии (название, услуги, цены, залы, график, фото). Он нужен
**только для первичной заливки**. Как только владелец впервые вошёл в кабинет и что-то
поменял — источником правды становится база, а файл больше ничего не перезаписывает
(команда заливки без флага `--force` существующую студию пропускает).

## 2. Supabase глазами разработчика, который знал только обычный API

Если вы писали бэкенд на Express/FastAPI, сопоставьте так:

| В обычном API | У нас в Supabase |
|---|---|
| Свой сервер с роутами (`app.get('/services')`) | **Не пишем для чтения вообще**: база сама отдаёт REST API на каждую таблицу (генерируется автоматически, называется PostgREST) |
| Код авторизации в middleware каждого роута | **RLS (Row Level Security)** — правила «какие строки таблицы можно видеть» живут в самой базе. Middleware больше не нужно: забыть проверку невозможно |
| `POST /bookings` с валидацией в контроллере | **Edge-функция** `create-booking` — это и есть ваш контроллер: TypeScript-файл, который получает запрос, валидирует (Zod) и пишет в базу. Живёт в `supabase/functions/` |
| JWT-библиотека + таблица пользователей | **Supabase Auth** — готовый вход по email/паролю, сессия, `auth.uid()` |
| S3-совместимое хранилище файлов | **Supabase Storage** — ведра (buckets) `portfolio` и `references` |
| Секретный ключ сервера (env) | **service_role key** — даёт всё; живёт ТОЛЬКО в edge-функциях и CLI, никогда в браузере |
| Публичный ключ (если был) | **anon key** — публичный, им пользуется сайт; RLS ограничивает его «только витрина» |
| Ваш сервер БД | Обычный **PostgreSQL**. Миграции — обычные SQL-файлы в `supabase/migrations/` |

Три ключевые мысли:

1. **Читать — можно прямо из браузера.** `supabase.from('services').select()` — это
   HTTP-запрос к автосгенерированному REST API. Безопасно, потому что RLS пропустит
   только публичные строки. Ровно как если бы у вас был GET /services без токена.
2. **Писать чувствительное — только через контроллеры.** Создание заявки, «моя запись»,
   помощник идут через edge-функции — аналог ваших POST-роутов с валидацией и
   лимитами. Клиент не может записать в `bookings` напрямую: у anon-ключа нет таких прав.
3. **Бизнес-инварианты — в базе.** «Два человека не могут забронировать одно время»
   решено не кодом, а exclusion constraint в PostgreSQL: база физически отвергнет
   пересекающиеся интервалы, даже если два запроса пришли одновременно. Это как если бы
   `UNIQUE` умел работать с отрезками времени.

Как идёт типичный запрос «показать свободные слоты»:

```
Браузер ──POST /functions/v1/availability──► Edge-функция (Deno, TS)
                                            │ 1. Zod-проверка тела
                                            │ 2. rate-limit по IP
                                            │ 3. service_role: читает studios,
                                            │    bookings, booking_resources
                                            │ 4. считает слоты ядром из src/core
Браузер ◄─────── { slots: [...] } ──────────┘
```

Edge-функция — самый близкий аналог знакомого обработчика роута. Разница только в том,
что она деплоится командой `supabase functions deploy`, а не на ваш сервер.

## 4. Как это работает: потоки данных

**Выбор бэкенда.** В `src/backend/index.ts` одна проверка: есть ли в env
`VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Есть → боевой адаптер; нет → демо
(localStorage). Весь UI работает через интерфейс `Backend` и не знает разницы —
поэтому образец для фотографа и прод работают на одном коде.

**Витрина.** `loadStudio(slug)` — в боевом режиме supabase-js (anon-ключ) читает
настройки студии и витринные таблицы. RLS пропускает только публичное.

**Свободное время.** Форма вызывает edge `availability` → та собирает из базы все
интервалы занятости и считает слоты тем же ядром, что и демо. Фронт рисует полную
сетку: свободные кнопки, занятые — перечёркнуты.

**Заявка** — самый защищённый путь:

```
форма ──► edge create-booking:
   Zod-проверка → honeypot-поле против ботов → rate-limit по IP
   → цена пересчитывается НА СЕРВЕРЕ (той же функцией из src/core/price.ts)
   → RPC create_booking_rpc: ОДНОЙ транзакцией пишет заявку + блокировки ресурсов
     · идемпотентный ключ: повторное нажатие не создаёт копию
     · exclusion constraint: пересечение интервалов = отказ (двойная бронь невозможна)
   → уведомление владельцу в очередь
   ◄── секретный токен для «Моя запись»
```

**Кабинет.** Владелец входит по email (Supabase Auth). Каждый его запрос к таблицам
проходит RLS: пропускаются только строки его студии (через таблицу memberships).

**«Моя запись».** `/s/<slug>/my/<token>`: edge `my-booking` ищет заявку по секретному
`accessToken`. Отмена — только в окне, разрешённом правилами владельца.

## 5. Бизнес-правила ядра (коротко)

- **Цена:** фиксированный пакет или почасовая аренда; тариф часа зависит от дня
  (будни/выходные) и времени (день/вечер); адонсы за бронь/час/человека; доплата за
  выезд по зоне; предоплата % или фиксом; бронь через полночь тарифицирует каждый час
  по своему дню.
- **Свободное время:** окно недели + закрытые даты; интервал блокировки = подготовка +
  дорога + съёмка + уборка; услуге нужны специалист и/или зал — свободно, когда свободны
  все; «любой свободный» подбирает специалиста; лимит съёмок в день; отпуска; весь день;
  многодневные; UTC в базе, показ в таймзоне студии.
- **Статусы (10):** новая → подтверждена → предоплата → проведена → в обработке →
  сдана → завершена; отменена клиентом / отклонена / не пришёл.

Полный список правил — в комментариях тестов `tests/core/`.

| Действие | Гость (anon) | Владелец (authenticated) | Платформа (service_role) |
|---|---|---|---|
| Читать витрину | ✅ | ✅ | ✅ |
| Читать calendarToken | ❌ (иначе утечка iCal) | ✅ | ✅ |
| Создать заявку | только через edge-функцию | так же | ✅ |
| Заявки/клиенты | ❌ | только своей студии | ✅ |
| Настройки студии | ❌ | своей | ✅ |
| Slug / статус / токены | ❌ | ❌ (только платформа) | ✅ |
| Вписать себя в чужую студию | ❌ | ❌ | ✅ |
| Storage portfolio | читать | писать в свою папку | ✅ |
| Storage references (референсы) | ❌ | ❌ | ✅ (приватно) |

| `studios` | студия: settings JSONB (весь TenantSettings), slug, статус demo/active, токен календаря |
| `memberships` | «пользователь ↔ студия ↔ роль» — основа всех прав владельца |
| `specialists`, `halls`, `services`, `addons`, `portfolio`, `reviews` | витринные данные |
| `bookings` | заявки: клиент, цена, статус, accessToken, идемпотентный ключ |
| `booking_resources` | блокировки ресурсов (интервалы + exclusion constraint) |
| `closed_periods` | отпуска специалистов, закрытия залов/студии |
| `notify_outbox`, `push_subscriptions` | очередь уведомлений, push-подписки |
| `assistant_usage`, `rate_limits` | дневной бюджет модели, лимиты частоты |

## 7. Edge-функции (аналог POST-роутов)

| Функция | Метод | Что делает | Защита |
|---|---|---|---|
| `availability` | POST | слоты на дату | Zod, 60 req/мин/IP |
| `create-booking` | POST | создать заявку | Zod, honeypot, 10 req/мин/IP, цена на сервере, RPC |
| `my-booking` | POST | своя заявка, отмена | Zod, токен, правила отмены |
| `assistant` | POST | ИИ-помощник (клиент/владелец) | Zod, лимиты, бюджет, студия по slug/сессии — модель не влияет |
| `ics` | GET | .ics и лента владельца | секретные токены; деплой с `--no-verify-jwt` |
| `notify-dispatch` | POST | доставка очереди уведомлений | только service role |

## 8. Демо-режим (без сервера)

Нет env Supabase → всё работает на одном устройстве: витрина из
`public/tenants/<slug>/tenant.json`, заявки и кабинет в localStorage, занятые слоты
генерируются детерминированно, помощник отвечает заглушкой. Режим для образцов:
`pnpm dev` — и можно показывать фотографам. Прод-данные — только через Supabase.

## 10. Запуск Supabase

**А. Локально (нужен Docker):**
```bash
npm i -g supabase && supabase init && supabase start  # :54321, Studio :54323
supabase db reset                                    # применит обе миграции
supabase functions serve availability create-booking my-booking assistant ics notify-dispatch
# владелец: Studio → Authentication → Add user, затем SQL:
insert into memberships ("userId","studioId","role")
select id,'kadr-studio','owner' from auth.users where email='…';
# .env: VITE_SUPABASE_URL=http://localhost:54321 + ключи из вывода supabase start
pnpm tenant:push && pnpm dev
```

**Б. Облако:** проект → SQL Editor → 0001, затем 0002 → пользователь + memberships →
ключи в `.env` → `pnpm tenant:push` → `supabase link` → `supabase secrets set …` →
`pnpm exec tsx scripts/sync-shared.ts` → деплой функций (`ics` — c `--no-verify-jwt`).

**В. Self-hosted в РФ (локализация ФЗ-152):** `supabase/docker` на сервере
Selectel/Timeweb; миграции и функции те же, ключи в env контейнеров.

**Сайт:** `vercel` из корня; в Vercel задать `VITE_*`.

## 11. Безопасность и соответствие

Изоляция студий (RLS + memberships + колоночные гранты); чувствительные записи только
через серверные функции (Zod, honeypot, лимиты, цена на сервере); атомарность и
идемпотентность заявок; минимум ПДн, согласие с версией и временем, страница политики,
удаление данных клиента по запросу; демо-студии под noindex с плашкой, только
вымышленные тексты и сгенерированные заглушки; секреты не попадают в бандл сайта.

**Ограничения:** файлы-референсы сжимаются на устройстве, но приватная загрузка в
storage — в доработке (хранится количество); очистка референсов через 90 дней, онлайн-
оплата, адаптеры Telegram/MAX/VK — вторая очередь.

## 12. Что проверено, а что нет

**Автоматически:** typecheck; 30 юнит-тестов; 12 e2e (запись съёмки и аренды,
перечёркнутое занятое время, цена до отправки, «Моя запись», галерея, весь кабинет);
tenant-команды; сборка с per-tenant PWA.

**Нужна живая база (первый чеклист после подключения):** одновременная двойная бронь;
изоляция студия A↔B на RLS; исполнение edge-функций и помощника; уведомления;
установка PWA на реальных iOS/Android.

## 13. Чек-лист запуска в прод (менеджеру)

1. Supabase (облако или РФ-стенд) + Vercel + домен с SSL.
2. Миграции 0001 и 0002; пользователи-владельцы; строки в memberships.
3. По каждой студии: tenant:new → наполнение → validate → push (статус demo).
4. Деплой функций (+ секреты модели/почты/push; ics с --no-verify-jwt).
5. Юрист: политика и согласие (ФЗ-152), правила отмены.
6. Приёмка по живой студии: заявка → подтверждение → деньги → проведение → сдача →
   завершение; отмена в окне и вне; двойная бронь двумя вкладками; CSV; iCal; PWA.
7. Перевод в `active` (снимает плашку и noindex), мониторинг, бэкапы (PITR),
   контроль бюджета модели на студию.
